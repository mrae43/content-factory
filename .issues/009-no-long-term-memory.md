# No Long-Term Memory for Stable Facts or Preferences

> *This was generated by AI during triage.*

- **Category:** `enhancement`
- **State:** `needs-triage`
- **Source:** Step 6 audit against `harness-eng.md` (Phase 6 — Add Memory)

## Summary

The harness has no long-term memory for stable facts, user preferences, brand voice,
or validated knowledge. The blueprint requires: "Use long-term memory for stable facts
and preferences" — but no such store exists. Every pipeline run is a clean slate:
preferences are re-supplied as `pre_context` at submission time, verified claims
accumulate in the DB but are never surfaced as reusable knowledge, and there is no
mechanism to carry editorial decisions or brand constraints across jobs.

A `GLOBAL` scope is referenced in a comment in the garbage-collection code but is
never implemented — it is dead code that documents a missing feature.

## Evidence

- **No user/brand preference store:** The only preference mechanism is `pre_context`
  (`models.py:109`), a JSONB column submitted per-job. There is no lookup table for
  `device_id` → preferences history, no persistent tone/voice profile, and no way to
  say "this user always wants conservative language on topic X." The `CopywriterAgent`
  receives `story_directives` fresh each time (`agents.py:240-246`) with no reference
  to prior user behavior.

- **No cross-job fact validation:** The `FactCheckClaim` table (`models.py:224-258`)
  accumulates verified/unverified claims per job, but these are never queried to inform
  future pipeline runs. If Job A's Red Team already validated "US GDP grew 2.8% in Q4
  2025", Job B on a related topic must re-verify the same claim from scratch. The
  vector store has no scope or namespace for "previously verified facts."

- **No accumulated editorial knowledge:** Human approvals (`HUMAN_REVIEW_NEEDED` →
  `POST /api/v1/jobs/{id}/approve-script`) produce approval decisions that are applied
  to the current script but never captured as editorial rules or preferences for future
  jobs. "This user rejected a carousel format" or "this reviewer flagged causal claims
  on topic Y" is lost after the job completes.

- **`GLOBAL` scope is dead code (`workers/tasks.py:15`):**

  ```python
  async def cleanup_local_research_chunks(job_id: UUID, db: AsyncSession) -> dict:
      """
      Garbage Collection Step (End of Pipeline).
      Deletes all ephemeral (LOCAL) vector chunks for a completed job,
      but retains anything flagged as 'GLOBAL' for future AEO/RAG memory.
      """
  ```

  The docstring describes a `GLOBAL` scope that would retain high-value chunks across
  jobs. No code in the entire codebase ever writes `scope="GLOBAL"`. The `scope` field
  in `meta` (see `ingest_chunks` in `vector_store.py:46`) only ever receives `"LOCAL"`
  or `"RAW-CONTEXT"`.

- **No preference propagation in eval suite:** The `evals/evals-criteria.md` tests (Eval 1-8)
  test per-job correctness and quality. None test cross-job consistency, preference
  adherence, or knowledge reuse — reflecting the architectural gap.

## Checklist

- [ ] Is the appropriate memory type used for each data category? **No** — long-term
      memory is absent entirely. Stable facts, user preferences, brand voice, and
      editorial decisions have no persistent home.
- [ ] Is long-term memory scoped to genuinely stable data? **N/A** — no long-term
      memory exists to scope.
- [ ] Is retrieval memory used instead of stuffing docs into context? **N/A**

## Recommendation

1. **Implement the `GLOBAL` scope:** Introduce `scope="GLOBAL"` as a third vector store
   scope for chunks that should persist beyond a single job. Candidate chunks include:
   - High-confidence research chunks (similarity > 0.9, source verified)
   - User-approved scripts and their claim sets
   - Editorial decisions and format preferences per `device_id`

2. **Create a preferences/profile store:** A simple key-value table or JSONB column
   keyed by `device_id` that accumulates tone, angle, platform, and format preferences
   across jobs. Surface these to agents as a `user_profile` block in context.

3. **Index completed job outputs back into the vector store:** On `COMPLETED`, persist
   `refined_context` and high-confidence claims as `GLOBAL`-scoped chunks so future
   jobs on similar topics benefit from prior research and validation.

4. **Add eval criteria for cross-job memory behavior** in `evals/evals-criteria.md`:
   test that known-verified claims from prior jobs are surfaced without re-verification.
